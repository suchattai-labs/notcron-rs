# notcron

systemd timers, services and mounts without the crontab — a single static
Rust binary with a full-screen builder TUI.

This is the Rust remake of [notcron.sh](https://github.com/suchattai-labs/notcron),
the POSIX shell original. It keeps that tool's cron→`OnCalendar` translation
and grows a real unit builder around it: standalone services, mount and
automount units, lifecycle control, and an edit flow that reads generated
units back into the form.

```
notcron                                    # the builder (primary interface)
notcron list [--all] [--system]            # units notcron manages
notcron add "0 3 * * *" /usr/bin/backup    # headless, from a cron expression
notcron remove backup                      # stop, disable, delete, reload
```

`--user` and `--system` are global: they may be given before or after the
subcommand, so `notcron --system list` and `notcron list --system` are the
same command. On the bare `notcron` they choose the scope the builder opens
in.

## Why

Cron jobs are easy to write and miserable to operate: no logs, no status, no
catch-up after downtime, environment surprises. systemd timers fix all of
that but make you write two unit files and remember four `systemctl`
invocations. notcron generates the units with sensible hygiene — journal
logging with a per-job `SyslogIdentifier`, `Persistent=true` by default, user
units unless you ask otherwise — and never touches anything it did not
create.

## Install

```sh
curl -fsSL https://raw.githubusercontent.com/suchattai-labs/notcron-rs/master/install.sh | sh
```

Installs into `~/.local/bin` (override with `PREFIX=/usr/local/bin`). Needs
curl or wget and nothing else. Linux x86_64 and aarch64.

Or grab the release asset yourself — `notcron-linux-x86_64` /
`notcron-linux-aarch64`, static musl builds with no runtime dependencies:

```sh
curl -fsSLo ~/.local/bin/notcron \
  https://github.com/suchattai-labs/notcron-rs/releases/latest/download/notcron-linux-x86_64
chmod +x ~/.local/bin/notcron
```

Or from source:

```sh
cargo build --release                              # ./target/release/notcron

rustup target add x86_64-unknown-linux-musl        # static
cargo build --release --target x86_64-unknown-linux-musl
```

## Ownership

**notcron only ever edits or removes units it generated.** Every generated
file carries a `# Generated by notcron` marker comment and an `X-NotCron=1`
directive, and timer/service pairs are additionally named `notcron-<name>`.
The marker *is* the definition of ownership. Foreign units — anything without
it — are hidden by default, revealed with `F`, shown greyed out, and can be
inspected (`status`, journal, raw file) but are refused for edit and removal
with a clear message. `notcron list --all` does the same on the command line.

Two consequences worth knowing:

**Mount units carry no `notcron-` prefix.** systemd derives a mount unit's
filename from its mount point — `/srv/my-share` *must* be
`srv-my\x2dshare.mount` — so there is nowhere to put a prefix. Ownership of
mount and automount units is decided by the marker comment alone. Strip the
comment and notcron will treat the unit as foreign.

**Unmodelled directives survive edits, inside a delimited block.** Anything
the form does not model is preserved verbatim under a
`# --- notcron:manual` header. For a unit notcron generated, parse → render
is byte-for-byte identical and enforced by tests. For a unit you hand-edited
afterwards, the *first* save normalizes: foreign directives are lifted out of
wherever you put them and collected into the manual block, so the file
changes shape once even if you changed nothing. Every save after that is
byte-stable. Nothing is dropped either way — diff the first save if you care
where a line ended up.

## The TUI

`notcron` with no arguments opens the list of managed units in the current
scope.

| key | action | key | action |
|---|---|---|---|
| `↑`/`↓`, `k`/`j` | move | `s` / `S` | start / stop |
| `Home` / `End` | first / last | `a` / `d` | enable / disable |
| `n` | new unit | `i` | `systemctl status` |
| `y` | copy the selected unit | `l` | journal, full-screen |
| `Enter`, `e` | edit (owned units only) | `v` | view the raw unit files |
| `x` | remove (stashed in the trash) | `r` | `daemon-reload` |
| `U` | undo a removal | `R` | run the job now |
| `t` | open/close the journal pane | `E` | export the unit's files |
| `f` | follow the journal live | `/` | filter the list |
| `u` | switch user ↔ system scope | `?` | help |
| `F` | show/hide foreign units | `q` | quit |
| click | select a row | `Esc` | clear the filter, then quit |
| wheel | move the selection | double-click | edit |

**`f` follows the journal**; the foreign-unit toggle it used to hold is now
shift-`F`. A follow belongs to a pane, and the pane is where anyone looks for
it — the toggle is the rarer key of the two.

The footer lists the bindings, dropping the least useful as the terminal
narrows. `? help` and `q quit` are the last two to go, and a binding is shown
whole or not at all.

### Health at a glance

The table shows what each unit last did and when it next runs:

```
   UNIT                      LAST      NEXT      STATE     SCHEDULE
 > notcron-backup.timer      exit 2    in 1h 49m failed    *-*-* 03:00:00
   notcron-sync.timer        ok        in 13h    inactive  *-*-* 15:00:00
```

**Failed units sort to the top**, in red, carrying the exit status that
explains them — `exit 2`, `killed`, `timeout`, `watchdog`, `throttled`. A
clean run is green. A unit systemd said nothing about shows `-` rather than
claiming to be fine.

`LAST` comes from `systemctl show` (`Result`, `ExecMainStatus`,
`ActiveState`); a timer's outcome is read from the *service* it drives, not
from the timer, which is almost always `success` regardless. `NEXT` comes
from `systemctl list-timers --output=json`, whose raw epoch timestamps can be
made relative without a date library.

**Columns are dropped as the terminal narrows, never wrapped.** At 80 columns
the health columns and the schedule all fit; below that the schedule goes,
then the state, and the unit name is the last thing standing. The name column
takes any slack, because a truncated unit name is the one thing that makes a
row useless.

### The journal pane

`t` opens a pane under the list with the last ten journal lines for the
selected unit. `f` follows it live.

Following spawns `journalctl -f` and reads it on a background thread, so the
UI keeps repainting whether or not the unit has anything to say. The child is
killed and reaped when the pane closes, when the selection moves and when
notcron exits — moving the selection ends the follow and says so, rather than
going quiet and looking broken. `--user` and system scope are handled
separately; `journalctl` has no `--system` flag, so the system journal is
asked for by omission.

### Filtering

`/` filters incrementally as you type. The filter searches everything on
screen — name, description, kind, schedule, state and the `LAST` column — so
`failed` finds the failures and `03:00` finds the three-in-the-morning jobs.
Several words all have to match, in any order.

`Enter` keeps the filter and returns to the list; `Esc` clears it. The header
shows the active filter and the title counts what survived it (`Units (1/7)`).
Arrows still move the selection while you type, so a match can be narrowed and
picked without leaving the field. `Esc` on an unfiltered list quits — it
unwinds one layer at a time.

### Run now

`R` starts the selected unit's **service** immediately, so a job can be tested
without waiting for its schedule. The timer is left alone and its next
scheduled run still happens. The health columns are re-read afterwards, so the
result of the run you just triggered is what you see.

### Export

`E` writes the selected unit's files to a directory of your choosing — the
same filesystem picker the builder uses — or shows them full-screen. A unit
notcron can model is re-rendered; anything else is exported as the bytes on
disk. **An existing file is never replaced without being named first**, and
the check happens before anything is written, so a refused export leaves the
directory untouched.

### Undo a removal

`x` no longer deletes: it moves the unit's files into a per-scope trash. `U`
browses it, newest first, and restores.

Restoring **never clobbers**. If a unit of that name exists again, the paths
that would be replaced are listed and you are asked; refusing moves nothing.
A unit that was enabled or running when it was removed is offered its old
state back, as a separate question. `x` inside the trash discards an entry for
good, with its own confirmation.

### Lingering

On the first user-scope run, if `loginctl` says lingering is off, notcron
warns that **user timers stop at logout** and offers to run
`loginctl enable-linger`. It is an explicit yes — nothing is enabled as a side
effect of starting notcron — and the prompt names the exact command and the
file it writes. Hosts where the state cannot be determined are not asked at
all, so a container or a non-systemd machine is never nagged.

Inside a builder form: `Enter` edits the selected field, `Tab`/arrows move,
`b` browses the filesystem for the selected path field, `v` cycles the side
pane, `c` reviews the advisory checks, `f` applies a suggested fix, `?` opens
the full help for the focused row, `p` previews the generated files, `Ctrl-S`
saves, `Esc` cancels. Inside a text field `Tab` completes instead — the field
prompt is modal, so the two never collide.

### The side pane

The builder carries a pane beside the form, cycled with `v`:

| pane | shows |
|---|---|
| **Field help** | what the focused row does, from `docs/field-help.md` |
| **Unit files** | the generated `.timer`/`.service`/`.mount`, live |
| **Next runs** | the next five times the timer will fire |
| **Checks** | the advisory checks, and which have a one-key fix |
| off | nothing; `v` again brings it back |

`PgUp`/`PgDn` scroll it. Everything in it follows the form as you type: the
unit-file pane re-renders on every edit, manual block included, so `p` is now
only for reading the files full-screen.

The pane is **on by default at 100 columns or wider and off below that**. A
permanent split does not fit an 80×24 terminal — the form needs 46 columns to
show a path next to its label — so on a standard terminal it is one keypress
away rather than always there. Turned on at 80 columns it still works; the
value column just gets shorter.

**Next runs** come from `systemd-analyze calendar`, merged across every
`OnCalendar=` line because systemd fires on their union. Interval and boot
timers have no calendar to analyse and say so instead of showing an empty
list, and a host without `systemd-analyze` gets "preview unavailable" — not an
error, since nothing is wrong with the schedule. The raw `OnCalendar` and cron
prompts show the same list live under the field as you type, recomputed once
typing pauses rather than once per keystroke.

### Advisory checks

`ExecStart=` is not run through a shell and is not resolved through `$PATH`,
which is the usual reason a command that works in a terminal fails as a unit.
The builder checks for that and a few neighbours — a relative or missing
binary, a non-existent `WorkingDirectory=`, `User=`/`Group=` in a user unit,
an `Environment` line that is not `KEY=VALUE`.

**None of it blocks a save.** The structural validation is the gate; this is
advice, shown in the status line and in the Checks pane, and `c` walks the
whole list.

Two of them come with the answer already computed, so `f` applies it on the
focused row:

```
warning: ExecStart=: 'rsync' is not an absolute path; systemd does not
         search $PATH — use '/usr/bin/rsync'          f -> /usr/bin/rsync -a ...
warning: ExecStart= contains shell syntax, but systemd does not use a shell
                                                     f -> /bin/sh -c "..."
```

The path fix keeps the arguments; the wrapper fix quotes the whole line.

### Completing paths, users and groups

`Tab` inside a text field completes to the longest common prefix first and
lists the candidates on the next press, as a shell does.

| field | completes |
|---|---|
| `ExecStart`, `ExecStartPre`, `ExecStopPost` | the program against executables, an argument against any path |
| `WorkingDirectory`, mount `Where` | directories |
| mount `What` | any path, for block-device and bind mounts only |
| `User` / `Group` | `/etc/passwd` and `/etc/group` |

Accounts are filtered to ones a job plausibly runs as — `root` plus uid ≥ 1000
with a real shell — because a distro's forty system accounts bury the three
that matter. `Ctrl-A` in the prompt widens it to all of them, so `www-data`
and `nobody` are one keypress away.

### Templates, copies and suggestions

`n` offers **From a template**: a nightly backup, a periodic sync, a cache
warmer. Each is a complete working unit — schedule, `Persistent=`, `Nice=`,
a mount-point guard — with an obvious placeholder command to replace, rather
than an empty form.

`n` also offers **From an existing unit**, and `y` on the list does the same
in one key: a copy of one of your units, renamed to something free
(`backup-copy`, then `backup-copy-2`) and marked as a copy in its
description. A mount clone renames `Where=` instead, since that is what its
filename is derived from. Nothing about the original's installed state comes
along — the copy is not installed until you save it.

Three fields prefill themselves, and only when they are empty:

- **Name** from the command, using the same derivation `notcron add` uses, so
  the same job named in either place comes out identical.
- **WorkingDirectory** from the directory notcron was started in.
- Mount **Where** from **What** — `//server/share` suggests `/mnt/share`,
  `/dev/disk/by-uuid/1234abcd…` suggests `/mnt/disk-1234abcd`.

Anything you typed is never overwritten.

### Browsing for paths

Every field that holds a path takes `b`, which opens a filesystem picker
instead of making you type it. Typing still works exactly as before — the
picker is an alternative, never a requirement.

| field | picks | filled in as |
|---|---|---|
| `ExecStart` | a file | the program, arguments preserved |
| `ExecStartPre`, `ExecStopPost` | a file | the program, arguments preserved |
| `WorkingDirectory` | a directory | the whole value |
| mount `Where` | a directory | the whole value, unit name re-derived |
| mount `What` | a file or directory | the whole value |

`What` only offers the picker for block-device and bind mounts. For NFS and
CIFS it holds `server:/export` or `//server/share`, which are not local paths,
so `b` is inert there and you type them as usual.

The picker opens on the field's current value — the directory itself, or the
parent of a file, or the nearest ancestor that exists — falling back to `$HOME`
and then `/`.

| key | action | key | action |
|---|---|---|---|
| `↑`/`↓`, `k`/`j` | move | `Enter`, `→`, `l` | descend, or select |
| `Home` / `End` | first / last | `←`, `Backspace`, `h` | parent directory |
| `PgUp` / `PgDn` | page | `H` | show/hide dotfiles |
| `Esc` | cancel, leaving the field alone | `Ctrl-S` | take the current directory |

Directories sort before files, carry a trailing `/`, and a `[ use this
directory ]` row at the top confirms wherever you are — so a field wanting a
directory never makes you descend into a file to get out. Fields wanting a
file do not list that row. A directory you cannot read reports why in the
status line and leaves you where you were.

`n` offers three builders.

**Timer + service.** Command, schedule, `Persistent=`, `RandomizedDelaySec=`,
and the common `[Service]` knobs (`Type=`, `WorkingDirectory=`, `User=`,
`Group=`, `Environment=`, `ExecStartPre=`, `ExecStopPost=`). The schedule step offers
every N minutes, every N hours, daily at HH:MM, weekly on a weekday, monthly
on a day of the month, at boot after a delay, a cron expression, or a raw
`OnCalendar` spec. Every resulting `OnCalendar` value is checked with
`systemd-analyze calendar` and the next elapse is shown in the status line as
you edit.

**Standalone service.** The same `[Service]` fields plus `Restart=` /
`RestartSec=` and the `WantedBy=` target. The target list follows the scope,
because the two managers do not share one: a system unit is offered
`multi-user.target`, `graphical.target` and `network-online.target`, a user
unit `default.target`, `basic.target` and `graphical-session.target`, and both
`timers.target`. This matters — enabling a user unit into `multi-user.target`
succeeds, creates the symlink, and then never starts, because the user manager
has no such target. Switching scope moves the value with it.

**Mount / automount.** `What` / `Where` / `Type` / `Options`, with presets for
block devices, NFS, CIFS and bind mounts that fill in a sane fstype and
option string, plus an optional companion `.automount` with
`TimeoutIdleSec=`. The unit filename is derived from the mount point using
systemd's own escaping rules, implemented natively and tested against
`systemd-escape --path`.

### Mount options

`Options` is a toggle menu, not a text field. It lists the options that are
worth setting for the `Type=` you chose, ticks the ones already set, and shows
the composed `Options=` string live as you work.

| key | action |
|---|---|
| `Space` | toggle the option under the cursor |
| `Enter` | toggle a flag, or prompt for a `key=value` option's value |
| `?` | the full explanation of the focused option |
| `Delete` | clear the option |
| `Ctrl-S` | apply |
| `Esc` | discard (confirmed, if you changed anything) |

Every filesystem gets `ro`/`rw`, `noatime`/`relatime`, `nofail`, `noexec`,
`nosuid`, `nodev`, `defaults` and `_netdev`. On top of that, NFS adds `vers=`,
`hard`/`soft`, `timeo=`, `retrans=`, `rsize=`/`wsize=` and `bg`/`fg`; CIFS adds
`credentials=` (which opens the file picker), `username=`, `uid=`/`gid=`,
`vers=` and `iocharset=`; a bind mount adds `bind`/`rbind`.

Options that contradict each other are one setting with two positions rather
than two checkboxes — turning on `ro` turns off `rw`, in place, so the option
that wins is not decided by which you happened to click last. Value prompts
are seeded from the documented example for that option, and a value containing
a comma is refused, since it would silently become two options.

**`x-systemd.*` options are deliberately absent.** `x-systemd.automount`,
`x-systemd.requires=`, `x-systemd.device-timeout=`, `x-systemd.mount-timeout=`,
`x-systemd.makefs` and `x-systemd.growfs` are read by
`systemd-fstab-generator`, which is not involved in a unit file at all: put
`x-systemd.automount` in a `.mount` unit and no automount unit is generated,
put `x-systemd.requires=` there and no `Requires=` appears. Both were probed
on a live host to confirm it. For automounting, use the builder's **companion
`.automount`** toggle, which writes the real unit; for a dependency, write
`Requires=`/`After=` in the manual block. (`nofail` and `_netdev` were probed
the same way and *are* honoured in a unit file, so both stay on the menu.)

Options the menu does not offer are never lost. Anything it cannot represent —
the `x-systemd.*` family, `file_mode=`, an option from a filesystem you are not
using — is collected into an **other options** entry, editable as free text and
written back in its original position. Opening someone else's mount unit,
changing one thing and saving cannot silently drop the rest, which is the same
bargain the manual block strikes for directives elsewhere.

The per-option help is generated from `docs/field-help.md`, which is embedded
at build time; the text you read in the TUI and the text in the repo are the
same string. So is the help pane for every builder field, the labels in the
schedule chooser and the `?` help on the list screen — a test asserts that
every row, preset and action resolves to an entry, so a new field cannot ship
with a blank pane.

Every builder has a **manual directives** row that drops into a free-text
editor for arbitrary extra lines — whole `[Section]` blocks are fine. That is
the escape hatch for edge cases the form does not model; see
[Ownership](#ownership) for how those lines are stored.

Opening an owned unit parses the files back into the builder: modelled
directives become form fields, everything else lands in the manual block.

### Saving over an existing unit shows a diff

Saving a unit that is already installed does not just ask "overwrite?" — it
shows a coloured line diff of every file, old against new, and writes nothing
without a `y`. Long runs of unchanged lines are folded away; `n`, `q` and
`Esc` all cancel.

The diff is against **what is on disk right now**, not against what the
builder read when it opened. If someone edited the file underneath you — or
deleted it, or created it — the review says so in the title bar and above the
offending file, so an overwrite that would lose someone else's change is
never a surprise. The diff is a plain LCS written out in-tree; it costs no
dependency.

## The CLI

Three verbs. The TUI is the primary interface; these exist so notcron can be
driven from a provisioning script.

```
notcron list   [--user|--system] [--all]
notcron remove [--user|--system] <name>
notcron add    [--user|--system] [options] "<cron>" <command> [args...]
```

`add` options:

| flag | effect |
|---|---|
| `--name <name>` | unit name (default: derived from the command) |
| `--description <text>` | `Description=` |
| `--shell` | run the command through `/bin/sh -c` (implied by shell metacharacters) |
| `--persistent` / `--no-persistent` | catch up on runs missed while powered off (default: on) |
| `--random-delay <span>` | `RandomizedDelaySec=`, e.g. `30s`, `5m` |
| `--workdir <path>` | `WorkingDirectory=` |
| `--env KEY=VALUE` | `Environment=`, repeatable |
| `--run-as <user>` | `User=` (system units only) |
| `--dry-run` | print the unit files instead of installing them |

```sh
# nightly backup, user scope, enabled and started
notcron add --name backup "0 3 * * *" /usr/local/bin/backup.sh --full

# a pipeline — quoted as one argument, so it gets /bin/sh -c automatically
notcron add "0 * * * *" 'df -h | mail -s disk me@example.com'

# system scope, jittered, with an environment
notcron add --system --name certbot --random-delay 30m \
    --env 'PATH=/usr/local/bin:/usr/bin' "0 4 * * *" /usr/bin/certbot renew -q

# see what it would write, install nothing
notcron add --dry-run "*/5 * * * *" /bin/true

notcron list --all          # include foreign units, read-only
notcron remove backup       # accepts 'backup' or 'notcron-backup'
```

`remove` refuses any unit notcron did not create.

## Scope

User units in `~/.config/systemd/user` are the default — no sudo, and they
survive logout if you have `loginctl enable-linger`. System units in
`/etc/systemd/system` are one keypress (`u`) or one flag (`--system`) away;
those writes go through `sudo`. Every `systemctl` and `journalctl` invocation
carries the matching `--user`/`--system` flag.

Mount and automount units are system-scope by nature and the builder says so.

## Cron syntax

5-field expressions: `minute hour day-of-month month day-of-week`. Supported
in every field — `*`, `*/N` steps, ranges `a-b`, stepped ranges `a-b/N`,
open-ended steps `a/N`, comma lists, and month/weekday names
(case-insensitive). Plus the macros `@hourly` `@daily` `@midnight` `@weekly`
`@monthly` `@yearly` `@annually` and `@reboot` (which becomes `OnBootSec=`
rather than `OnCalendar=`).

| cron | `OnCalendar=` |
|---|---|
| `0 3 * * *` | `*-*-* 03:00:00` |
| `*/15 * * * *` | `*-*-* *:00,15,30,45:00` |
| `0 */6 * * *` | `*-*-* 00,06,12,18:00:00` |
| `0 9-17 * * *` | `*-*-* 09,10,11,12,13,14,15,16,17:00:00` |
| `0 8-18/4 * * *` | `*-*-* 08,12,16:00:00` |
| `30 2 1,15 * *` | `*-*-01,15 02:30:00` |
| `0 9 * * mon-fri` | `Mon,Tue,Wed,Thu,Fri *-*-* 09:00:00` |
| `0 0 1 mar-may *` | `*-03,04,05-01 00:00:00` |
| `@weekly` | `Sun *-*-* 00:00:00` |
| `@reboot` | `OnBootSec=1min` |

Out-of-range values, inverted ranges, zero steps, unknown names and wrong
field counts are rejected with a message that names the problem, before
anything is written.

One semantic gap needs care. Where cron ORs a restricted day-of-month against
a restricted day-of-week, systemd ANDs them — so notcron emits two
`OnCalendar=` lines, which systemd ORs, preserving the cron meaning:

```
# 15 10 13 * fri
OnCalendar=*-*-13 10:15:00
OnCalendar=Fri *-*-* 10:15:00
```

## Differences from notcron.sh

Coming from the shell version:

- **The TUI is the product now.** `notcron` with no arguments opens a
  persistent list-and-edit screen, not a one-shot creation wizard. Units can
  be edited after the fact.
- **More than timers.** Standalone services and mount/automount units, which
  the shell version never did.
- **Three subcommands instead of a flag soup.** `list`, `remove`, `add`.
  `notcron.sh --every 15m ...`, `--boot`, `status` and `logs` have no CLI
  equivalent — the interval and boot schedules live in the builder, and
  status/journal are `i` and `l` in the TUI.
- **`add` takes a cron expression only.** Positional schedule, then the
  command as trailing arguments.
- **Ownership is a marker comment**, not just a name prefix — which is what
  lets mount units, whose filenames systemd dictates, be owned at all.
- Same cron translation, same `Persistent=true` default, same user-scope
  default, same MIT license.

## Tests

```sh
cargo test
```

Covers the cron translator (every case from the shell suite, including the
rejection cases), unit generation, parse round-trip losslessness, systemd
path escaping checked against the real `systemd-escape`, the text editor
buffer, the advisory checks and their fixes, completion, the line diff, the
filter's matching, health sorting and `systemctl show` / `list-timers`
parsing from captured output, and TUI layout at terminal sizes down to 1×1 —
including the builder painting every pane mode at every size, and the list,
journal pane, diff review and trash view each fitted exhaustively across a
grid of tiny frames. Tests that need
`systemd-analyze` or `systemd-escape` skip themselves when those binaries are
absent, so CI without systemd stays green.
